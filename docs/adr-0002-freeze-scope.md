# ADR-0002：证据包冻结范围

**状态**：已接受（2026-10-21，待实现后冻结）　**替代**：ADR-0001 中“先冻结 v0.1”的顺序
**影响**：K4、多版本修订、schema、验证器、试点准入

## 背景

ADR-0001 的四个决定仍然有效，但它建议“先写回 v0.1 文字再冻结，随后做 K4 与多版本”。评审指出这会返工：

- K4 会向 manifest 增加密钥时间线（轮换/撤销/继承关系），并改变“每条记录用哪把钥验证”的语义；
- 多版本交付会改变 `delivery_id` 的稳定性、修订关系、验收引用与冲突处理；
- 现有 schema 拒绝未知字段，后加字段会直接破坏兼容性。

因此不应把冻结当成文字收尾。**冻结条件是：目标试点所需的证据能完整导出，并被另一方按稳定规则核验。**

## 决定

选择**路径二**：先补最小 K4 与修订语义，跑通端到端样例，再冻结。冻结目标命名为 **evidence-pack v0.2**；v0.1 保留为历史草案，不再冻结。

### 纳入冻结范围（最小集）

1. **K4：密钥时间线**
   - manifest 增加 `identity.history`：按序记录 `register / rotate / revoke` 事件（seq、pub、old/new、kind、effective_at、suspected_leak_at）；
   - 验证器按记录所在账本序号选择当时有效的钥；轮换条目由旧钥签名、携带新钥证明；
   - 导出轮换/撤销后的真实桥，接收方可离线核验“这条记录当时由谁签”；
   - 撤销不追溯否定历史；疑似泄露输出“身份可信性不确定”，不输出单一有效/无效。
2. **最小修订语义**
   - `delivery_id` 在修订间保持不变，`version` 递增，`previous_version` 指向上一版；
   - 拒收记录必须绑定被拒版本与理由；修订后重新验收绑定新版本；
   - 同一版本出现多个冲突验收 → 验收轴 `unknown`，不自动裁决；
   - 验收已过期版本时仍可验证，但必须显式标记“已被后续版本取代”。
3. **信任输入配套**
   - 外部信任输入增加 `expected_key_history`（可选）或至少 `expected_actors` 的时代划分；
   - 撤销状态文件仍外置，发布者公钥独立交付；
   - 锚点回执仍需 `bridge_id` 与精确检查点。

### 明确排除（不进入 v0.2 冻结）

- K3 紧急恢复（旧钥丢失/泄露的预授权机制）：试点用人工处置流程，写入试点准入，不写进 v0.2 承诺；
- 附件内容复核（固定 `hashes_only`，内容轴 `not_executed`）；
- 多任务批量导出、项目隔离、保留策略、加密、退出托管（P 系列）；
- 跨桥/跨组织的密钥联邦。

## 冻结条件

- [ ] 真实桥端到端样例跑通：提交 v1 → 拒收 → 修订 v2 → 验收 v2 → 双方导出 → 接收方离线核验；
- [ ] 样例覆盖 K4（轮换后导出）与撤销（退役/疑似泄露）两类身份场景；
- [ ] 协议、schema、参考验证器、产品验证器四者一致，固定向量覆盖上述路径；
- [ ] 不支持场景显式拒绝或标记 `unknown`，不得静默通过；
- [ ] B1/B2/B7/B6 的文字与 schema 同步完成；
- [ ] 发布带着明确支持范围的版本：bridge 0.8.x+；旧包按旧规则验证。

## 后果

- 在 v0.2 冻结前，不承诺跨版本兼容；实现可继续演进；
- 试点准入必须书面说明 K3 的人工处置流程（谁撤销、哪些操作停止、历史如何保留）；
- v0.1 的 16 个固定向量继续作为回归基线，新增 K4/修订向量后总数增加。
